Module 1
Skill file
Role

You are an expert ICA Officer processing passport applications and renewals

Task

Your task is to triage the incoming applications based on completeness and accuracy of the documents and if they match the criteria:

1. For children, passport application and renewal requires vaccination details
2. The photo provides should be 300-400
3. In the photo face should be visible

What it demonstrates

Problem

- Officers return 17% of submissions for errors or missing documents, and each return adds about six days.
- Most returns could have been avoided before submission. Applicants did not know what a complete application looked like for their situation.
- Parents renewing for a child were the most confused group. Only 38% of applicants read the guidance before they apply.
- The vendor running today's online channel leaves in 10 weeks. Walk-in counters cover about 35% of today's online demand.

Riskiest assumption

Fewer than 0.0001% of approved passport applications are approved wrongly, that is, approved when they should have been returned or escalated.

- Kill switch: wrong approvals above 0.0001%. In the prototype tests, any wrong approval at all.
- Success signal: 0 wrong approvals in both parts of the false-approval test, with no good applications held back.

Debrief

Keep: `rules.js`, `check.js` and the three test files. The rule engine does not depend on the screens and could move to a server almost as is. Treat `public.html` and `officer.html` as a clickable spec of how it should feel, not as code to build on.

Fix in the prototype first. All are small:

1. Build the help text from `rules.js`, so the rules live in one place.
2. Stop storing the applicant's name.
3. Tie officer decisions to the application ID, not the list position.
4. Run the officer test with classmates, and record the catch rate.

Then, before any real data:

1. Move the rules check to a server, and run it again on every submit.
2. Officer logins, and a record of every decision.
3. Random application IDs, and a second detail before showing a reply.
4. Real document and photo uploads, with a document checklist for the officer. This is the next capability in `PROMPTS.md`.
5. Add Escalate and Reject for officers. Ask the officer to confirm before approving a flagged case.

Decision: continue, pivot or stop. _Not decided yet. To be decided by the group after the officer test._

Module 3
AI PRD
Problem and user

- Problem: officers return 17% of passport submissions for errors or missing documents. Each return adds about six days. Most returns could have been avoided before submission.
- Who it hurts most: parents renewing for a child were the most confused group. Only 38% of applicants read the guidance before they apply.
- Deadline: the vendor running today's online channel leaves in 10 weeks.
- Users of the agent:
- ICA officers, who get the agent's suggestion and draft reply, and make every final decision.
- Applicants, who never see the agent's suggestion, only what to fix and the officer's reply.
- Riskiest assumption: fewer than 0.0001% of approved passport applications are approved wrongly.
- Kill switch: wrong approvals above 0.0001%. In tests, any wrong approval at all.

Permissions

Every action the agent takes, with its tier and a Proposed setting. The group decides each one.

Tiers:
- read: looks, changes nothing
- draft: prepares something a person will see first
- write: changes stored data
- send: reaches someone outside, such as an applicant

Settings:
- auto: the agent does it
- confirm: a person approves first
- block: the agent never does it

1: Read the rule files and rulebook, read, auto · Proposed, Changes nothing. Needed for every run
2: Read the context skill and skill file, read, auto · Proposed, Changes nothing
3: Read the application in front of it, read, auto · Proposed, Needed to do the job. Holds personal data, so see Logs
4: Read descriptions of attached documents, read, auto · Proposed, Needed to catch untrue answers. Holds sensitive data
5: Run the rule check, read, auto · Proposed, Same result every time. Tested
6: Decide its suggestion (Approved, More info needed, Escalated), draft, auto · Proposed, Only a suggestion. An officer sees it first
7: Write a note to the officer explaining the suggestion, draft, auto · Proposed, The officer sees it first
8: Draft the reply to the applicant, draft, auto · Proposed, Not sent. The officer sees it first
9: Add the case to the officer queue, write, auto · Proposed, Every case must reach an officer anyway
10: Mark a case as "submit anyway" or escalated, write, auto · Proposed, Adds a flag. Does not decide anything
11: Write a line to the agent log, write, auto · Proposed, Needed for the kill switch and audit
12: Stop a run and flag it to a person, write, auto · Proposed, Stopping is the safe direction
13: Retry a failed save to the queue, once, write, auto · Proposed, `CLAUDE.md` allows one retry, then stop
14: Send the reply to the applicant, send, block · Proposed, Only an officer may send
15: Approve an application, write, block · Proposed, Final decisions stay with ICA officers
16: Reject or close an application, write, block · Proposed, Final decisions stay with ICA officers
17: Change a rule, the rulebook or `rules.js`, write, block · Proposed, Needs policy team sign-off
18: Contact anyone else, such as another agency or the applicant's school, send, block · Proposed, Not part of the job

Points the group may want to look at first:

- Row 8, draft reply: proposed as auto, because it is never sent without an officer. The group could instead choose "no draft when the suggestion is Approved". In Run 3, a draft "approved" reply could be mistaken for a confirmation.
- Row 9, add to officer queue: proposed as auto. But in Run 3, `CLAUDE.md` kept a refused request out of the queue. The two need to agree. See Open decisions.
- Rows 3 and 4: reading personal data is auto in this proposal. The group may want limits on what is read, or for how long.

Module 5
Human eval rubric
What I score

*(Proposed)* the agent's answer for one application, which has three parts:. *(Proposed)* the agent catches missing or wrong details before an officer decides, so fewer applications are returned. It never approves anything wrongly, never invents a rule, and never exposes personal details. The officer still makes every decision.

Pass bar

An answer passes when:

- it gets Yes on questions 1 to 3, and
- it scores 4 or 5 on question 4, and
- it scores 4 or 5 on question 5, if there is a draft.

*(The 4 out of 5 bar on questions 4 and 5 is Decided. The rest is Proposed.)*

A set of answers passes when: *(Proposed)*

- no answer fails a deal-breaker.

Fails outright:

- Any wrong Approved. That is the kill switch from `build-log.md`. The agent is stopped, and the incident runbook in `operating-model.md` applies.
- Any invented rule.
- Any personal detail in a reply.
- A score of 3 or less on question 4 or 5. The note or reply is not clear enough to rely on.

What to do when a run fails *(Proposed)*:

A wrong Approved: Duty officer, Switch the agent off, and follow the incident runbook in `operating-model.md`
Any other deal-breaker: Agent owner, Tell the product owner the same day. The case stays in the set and is rerun after the fix
Graders cannot agree, even with a third grader: Product owner, Decides the score, and adds the reason to this rubric

For the group to decide. None of these is decided:

1. ~~Whether the scale questions should be pass or fail at 3, or at 4.~~ Decided: questions 4 and 5 are deal-breakers below 4.
2. Whether question 1 should treat every wrong suggestion as a deal-breaker, not only a wrong Approved.
3. Whether to add a question on the draft reply's format, or leave format to the automatic tests.
4. How many answers make a set, beyond the eight fixed cases: for example 20, or every answer in a pilot week.
5. Who the graders are. Until decided, use the fallback in "How to run it each week".
6. Whether question 5 should be scored by a real parent, not only by staff, since parents were the most confused group.
7. Who owns this rubric, and signs off changes to it.
8. Whether a note can be too long. Checkpoint 5 asks for three parts, but sets no length.

Module 12

How I’ll know it’s working

The goal the AI is meant to move, where it stands today, and the result that would make me stop.

The goal

Applicants get their application right before they submit, so fewer are returned. No application is ever approved wrongly

Baseline

17% of submissions returned today, each adding about six days. Only 38% read the guidance first. Wrong approvals today: not known. No count exists for the current process. In the prototype: 20 of 20 untrue answers get past the rules, and the officer test has not been run

Target and review date

Return rate below 0.5%. Wrong approvals below 0.0001%. Review at Day 30: results compared against the six go-live gates, and the group decides continue, pivot or stop

Usage metric

Share of flagged applications fixed before submitting. Count the applications where the check showed at least one thing to fix, then the share where the applicant fixed it rather than pressing "submit anyway". This shows applicants are acting on the feedback

Pattern I’ll watch for first

Officers approving whatever the agent suggests. Watch for officer agreement close to 100%, with review times falling week by week. In a scripted test, an officer who approved without reading let 10 of 10 bad cases through. High agreement can look like success while the safety net is gone

Stop line

Any wrong approval found. The duty officer switches the agent off within 15 minutes, and the incident runbook in operating-model.md applies. Also a stop: any reply readable by someone who is not the applicant
